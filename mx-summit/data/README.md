# The Sample Export

Everything in this folder is **made up**. Blue Ridge Property Management does not
exist. Neither do the properties, tenants, vendors, or owners. Any resemblance to
a real person or company is a coincidence.

The four CSVs are generated by `generate_sample_data.py`. It is seeded, so running
it again produces identical files. If you ever want to change the data (more
rows, a different mix, your own property names), edit that script and re-run it:

```
python3 mx-summit/data/generate_sample_data.py
```

## "Today" in this data

The export is anchored to **2026-09-22**. Nothing depends on the real date:
`pm_reader.as_of()` uses the newest timestamp in `melds.csv` as "today", so
"overdue", "scheduled today", and "completed in the last 24 hours" keep working
no matter when you open this.

## Column names vs. Property Meld's API

Where it made sense, columns use the same names Property Meld's public API v2
uses, so anything you build here maps cleanly onto live data in Session 2.
Where we simplified, it says so.

### melds.csv

| Column | Property Meld API | Notes |
|---|---|---|
| `id` | `id` | |
| `brief_description` | `brief_description` | The one-line title |
| `description` | `description` | What the tenant reported |
| `status` | `status` | `PENDING_ASSIGNMENT`, `OPEN`, `PENDING_COMPLETION`, `COMPLETE`, `MANAGER_CANCELED` |
| `priority` | `priority` | `LOW`, `MEDIUM`, `HIGH`, `EMERGENCY` |
| `work_category` | `work_category` | We use 5: `PLUMBING`, `HVAC`, `ELECTRICAL`, `APPLIANCE`, `GENERAL`. The real API has more. |
| `created` / `updated` | `created` / `updated` | |
| `due_date` | `due_date` | |
| `assigned_at` | **simplified** from `vendor_assignment_requests[].accepted_at` | When the vendor accepted the job |
| `scheduled_start` | **simplified** from `vendorappointment[].scheduled_start` | The appointment |
| `marked_complete` | `marked_complete` | Blank unless status is `COMPLETE` |
| `property_id` | `prop` | |
| `unit_id` / `unit` | `unit` / (from `/units/`) | Unit id and its short name |
| `unit_address` | `unit_address.full_address` | Flattened to a string |
| `tenant_name` | **simplified** | The API keeps residents on a separate endpoint; we inline a name for readability |
| `vendor_id` / `vendor_name` | `vendor_assignment_requests[].vendor` / `.vendor_name` | The accepted vendor |
| `estimate_total` | **simplified** from `/estimates/` `total` | Inlined so you don't need a second file |
| `invoice_amount` | **simplified** from `/invoices/` `amount` | What the job actually cost |
| `tenant_rating` | `tenant_rating` | 1–5, present on some completed melds only |

In `api` mode, `pm_reader` fills `tenant_name`, `estimate_total`, and
`invoice_amount` with blanks, because those live on other endpoints. The
blueprints handle blanks gracefully. Session 2 is a good place to add them.

### vendors.csv

`id`, `name`, `email`, `phone`, `is_active` match the API. `categories` is the
API's list joined with `|`.

### properties.csv

`id`, `property_name`, `line_1`, `city`, `county_province` (state), `postcode`,
`is_active` match the API. `unit_count` is the length of the API's `units` list.
`owner_id` is the first entry of the API's `owners` list.

### owners.csv

`first_name`, `last_name`, `email` are the API's nested `user` object,
flattened. `properties` is the API's list joined with `|`.
